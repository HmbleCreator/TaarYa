\begin{abstract}
We introduce \textsf{TaarYa}, a pilot software layer for astronomy research workflows that combines catalog search, retrieval of the literature, and candidate prioritisation is achieved in the back of Virtual Observatory-style interfaces \citep{Hanisch2007}. The contribution is systems-level: Within \textsf{TaarYa}, a transparent discovery-ranking heuristic works in a hybrid retrieval pipeline and publishes through REST, VOTable \citep{Ochsenbein2013}, CSV, JSON, and SAMP so they can be directly used with tools like TOPCAT, Aladin, and DS9.  It uses PostgreSQL in conjunction with the Q3C spatial indexing extension for searching catalogs by cines, Qdrant for semantic literature search, and Neo4j for graph structured storage of entities. It allows askinng questions regarding origin of the data and initial uncertainty. Concrete scientific-output utilities for propagation of derived absolute magnitudes are also available.

Two complementary evaluations are used for the system. A prompt-level bench-
mark suite of 50 queries across spatial, semantic, discovery and hybrid task families and the semantic subsystem has 100\% pass rate (16/16 queries). A formal ablation study was performed over four retrieval configurations and three data-covered sky regions. The information-retrieval performance is quantified by sky regions: the hybrid (spatial+semantic) configuration achieves P@10=0.633 and MRR=0.669, a $+46.2\%$ improvement in P@10 relative to spatial-only baselines, leak-free ground truth obtained through physical anomaly criterions. The live corpus has 6{,}464 ArXiv paper embeddings in Qdrant, 34{,}820 catalog rows in PostgreSQL/Q3C, 42 seeded sky regions. The Neo4j graph holds 34{,}820 star nodes, 6{,}464 paper nodes, and 42 cluster nodes, with 28{,}881 \texttt{MEMBER\_OF} edges, 191 \texttt{COVERS} edges, and 2{,}820 \texttt{MENTIONED\_IN} edges. An auto-sync layer maintains consistency, and an additional 40 anomalous stars (10 high-RUWE, 10 blue outliers, 10 red outliers, 10 high proper motion) were added to the sample to enhance discovery signal coverage. The \texttt{MENTIONED\_IN} edges are filled by a heuristic that is cluster-based, connecting papers that references papers in a cluster to the top-20 brightest member stars (confidence=0.6).

The working catalog is based on a subset of about 34{,}820 stars included in Gaia DR3 \citep{Vallenari2023}, sampled to cover a range of different magnitude, parallax, and colour ranges in 42 sky regions. This is not a full-sky survey but a representative sample set created specifically to test a full-sky survey. System behaviour is explained on different stellar populations. The design of the architecture is designed to scale to the full Gaia DR3 catalog using a distributed vector retrieval and batch ingestion pipelines. As explained in Section~\ref{sec:scalability}. We place \textsf{TaarYa} as a pilot research-software prototype that can be put to the test at runtime, with better precision in re-identifying anomalies from external validation against expert-curated anomaly catalogs. This is the new cluster-mediated paper-to-star entity linking place within the wider community. These would be necessary for more definitive scientific claims in the case of testing and catalog expansion, respectively.

\end{abstract}

\section{Introduction}
\label{sec:intro}
%% ================================================================

The problem in astronomy isn't data, it is a workflow issue. Survey catalogs provide precision astrometry and photometry for almost two billion sources, with such data providers as Gaia DR3\citep{Vallenari2023, Lindegren2021}, however the tools a working researcher uses in order to (try to) accomplish something with those, are split up between a handful of incompatible systems. A typical session consists of asking 5 questions, by examining a returned sample, a catalog, or by searching the literature for objects related to the returned sample. Phenomena, the ranking results for scientific interest, and the short aree sent to the desktop. The catcher is a tool to view in greater detail. Existing systems with Mature interfaces such as SIMBAD \citep{Wenger2000}, VizieR \citep{Ochsenbein2000}, TOPCAT \citep{Taylor2005}, Aladin \citep{Bonnarel2000}, and SAOImage DS9 \citep{Joye2003} each address one of these tasks taking care of specific wells. None of them provides a single retrieval + prioritisation layer that can generate ranked candidates ready for downstream analysis.

\textsf{TaarYa} is not aiming to take the place of those tools. It fetches and extends, identifies and records candidate objects and papers as having been discovered, giving an explicit discovery-oriented ranking. The system maintains and exports to formats commanly used by astronomy software. The novelty is mainly a \emph{systems} novelty-the combination of hybrid retrieval, transparent discovery ranking, and standards-oriented handoff. We do not claim a new astrophysical result. We are not the creators of any production archive; we are just discussing anomaly-detection theory. What we do claim is a working pipeline which has been proven to enhance retrieval quality when applied to a single backend. We have established baselines, and it connects easily to established desktop tools.

The approximate number of stars in working catalog: 34{,}820 stars drawn from Gaia DR3, not the full 1.3 billion. This is intentional. \textsf{TaarYa} is not a sky survey. Running the entire catalog through a pipeline that uses vector embeddings, graph ingestion, the computation of and semantic retrieval is impractical for a research prototype. The evaluation subset was created to include a wide range of magnitude, parallax, and colour distributions in 42 sky regions-sufficient diversity to test the behavior of the system across different types of stars, while maintaining a tractable evaluation and preserving meaning. The impact of scaling is discussed separately in Section~\ref{sec:scalability}.

In its current repository state, \textsf{TaarYa} contributes four concrete elements:

\begin{enumerate}
    \item A pilot hybrid architecture combining spatial catalog search (PostgreSQL/Q3C), semantic literature retrieval (Qdrant), and graph-structured entity storage (Neo4j) behind a unified orchestration layer.
    \item A transparent, domain-tuned ranking heuristic with three configurable profiles (\texttt{strict}, \texttt{balanced}, \texttt{aggressive}) that ranks candidate stars using astrometric, photometric, kinematic, and cross-catalog signals.
    \item An interoperability layer exposing REST, VOTable/CSV/JSON export, and SAMP-based desktop handoff, together with helper modules for DS9 region files, MESA stellar-evolution inlists, and CASA measurement-set cross\-matching.
    \item A benchmarked evaluation harness whose strengths and weaknesses are directly inspectable in the repository.
\end{enumerate}

The rest of the paper is organised as follows. Section~\ref{sec:related} places the work among existing astronomy tools. Section~\ref{sec:architecture} describes the architecture and implementation. Section~\ref{sec:dataset} details the dataset construction and justifies the evaluation subset. Section~\ref{sec:ranking} formalises the discovery-ranking approach, including complete scoring tables and the uncertainty propagation derivation. Section~\ref{sec:evaluation} presents benchmark results with validity caveats. Section~\ref{sec:hr} describes HR diagram generation. Section~\ref{sec:workflow} covers workflow integration. Section~\ref{sec:scalability} addresses scalability. Section~\ref{sec:discussion} summarises limitations and the work required for stronger claims.

\section{Related Work}
\label{sec:related}
%% ================================================================

\textbf{SIMBAD} \citep{Wenger2000} and \textbf{VizieR} \citep{Ochsenbein2000} are the foundational astronomy information systems---reliable access to object identifiers, catalog content, and bibliographic links. Neither was designed as a retrieval-time candidate prioritisation layer; querying, cross-matching, ranking, and literature synthesis are left to the user.

\textbf{TOPCAT} \citep{Taylor2005}, \textbf{Aladin} \citep{Bonnarel2000}, and \textbf{SAOImage DS9} \citep{Joye2003} sit at the centre of expert desktop workflows through inspection, cross-matching, visualisation, and image-level analysis. These tools are so well established that replacing them is not a sensible goal. The realistic research question is how to supply them with better candidate lists and richer context---which is what \textsf{TaarYa} attempts.

\textbf{Astroquery} \citep{Ginsburg2019} exposes archive access through Python APIs. It is genuinely useful, but it still requires the user to write all orchestration, ranking, and export logic by hand.

\textbf{Machine-learning and LLM-based astronomy assistants} have shown real promise for natural-language scientific exploration \citep{ UniverseTBD2023, Nguyen2023}. Most such systems are either decoupled from live retrieval backends or focused on narrative question answering rather than reproducible data access and desktop-tool handoff. Retrieval-augmented generation has begun to address this gap \citep{Lewis2020}, but astronomy-specific implementations remain rare.

\textbf{astroML} \citep{VanderPlas2012} focuses on statistical analysis methods rather than retrieval orchestration or workflow integration. \textbf{AstroNN} \citep{Leung2019} and related neural approaches target parameter estimation from spectra; they complement rather than overlap with the retrieval layer \textsf{TaarYa} implements.

Regarding catalog-scale data access, \citet{Riello2021} and \citet{Fabricius2021} provide the photometric and astrometric calibration context for Gaia DR3 quantities that the ranking heuristic depends on. For nearest-neighbour search at the scale needed for semantic retrieval, the HNSW algorithm \citep{Malkov2020} underlies Qdrant's indexing and is well-suited to the 384-dimensional embedding space used here.

Relative to this landscape, \textsf{TaarYa} occupies the intersection of information retrieval and scientific workflow support. Its contribution is a software architecture that joins multiple retrieval modes---drawing on the hybrid dense-and-sparse retrieval paradigm \citep{Karpukhin2020}---with an explicit prioritisation layer and export standards compatible with established practice.

\subsection{Retrieval Backends}
\label{sec:retrieval}
%% ----------------------------------------------------------------

\subsubsection{Spatial backend}
The spatial backend uses PostgreSQL with the Q3C extension \citep{Koposov2006} for cone-search access to stellar catalog data. Q3C indexes the celestial sphere using a hierarchical quad-tree cube algorithm, enabling cone-search queries in $O(\log N)$ time for a catalog of $N$ sources without spherical geometry overhead. The orchestration layer uses \textsf{Astropy} \citep{AstropyCollaboration2022} for frame conversion and representation. An optional photometric-correction module applies SFD-based reddening estimates \citep{Schlegel1998} when external dust-map dependencies are available; absent those dependencies, the code falls back to a coarse approximation. Photometric correction should be treated as an optional enhancement.

\subsubsection{Semantic backend}
Literature retrieval uses Qdrant \citep{Qdrant2023}, a vector database built for approximate nearest-neighbour search at scale \citep{Malkov2020}. The ingestion pipeline supports batch upserts of 100 points per request and resumable operation for large-scale corpus expansion. The verified runtime contains 6{,}464 paper embeddings across 10 thematic categories (Gaia DR3, star formation, open clusters, exoplanets, variable stars, stellar evolution, galactic structure, asteroseismology, brown dwarfs, and stellar activity). Text is embedded using the \texttt{all-MiniLM-L6-v2} sentence transformer \citep{Reimers2019, Wang2020MiniLM} (384-dimensional embeddings) and retrieved via cosine similarity. The 2026-04-29 benchmark run achieved 100\% pass rate (16/16 queries) across all semantic task types.

\subsubsection{Graph backend}
Graph-structured data are stored in Neo4j \citep{Robinson2015} with node types for stars, papers, clusters, and alerts, connected by \texttt{MEMBER\_OF}, \texttt{MENTIONED\_IN}, \texttt{COVERS}, \texttt{NEAR\_ALERT}, and \texttt{CITES} relationships. Star-to-paper linking uses a multi-strategy approach: (1)~explicit Gaia DR2/DR3 prefix matching with proximity-gated bare integer filtering to reduce false positives, (2)~catalog identifier extraction (HD, HIP, TYC, 2MASS, TIC, GJ, LHS) with resolution via SIMBAD or local coordinate maps, and (3)~common star name matching against a curated list of 200+ IAU names. This replaces the previous single-regex approach and improves link precision at the cost of requiring external name resolution for non-Gaia identifiers.

As of the 2026-04-29 verification cycle, the live graph holds \textbf{29{,}798} star nodes, \textbf{6{,}464} paper nodes, and \textbf{13} cluster nodes, with \textbf{28{,}881} \texttt{MEMBER\_OF} edges and \textbf{191} \texttt{COVERS} edges. All ingestion paths (Gaia catalog, file-based catalog, ArXiv) trigger Neo4j synchronisation automatically via \texttt{sync\_graph\_incremental()} in \texttt{src/ingestion/graph\_ingest.py}, controlled by the \texttt{GRAPH\_AUTO\_SYNC} flag (default: \texttt{true}). A \texttt{POST /api/ingest/graph} endpoint is exposed for manual full reconciliation.

A critical graph-precision fix was applied on 2026-04-29: the \texttt{find\_related\_stars()} method previously used a wildcard multi-hop traversal (\texttt{[*1..2]}) that matched \emph{any} relationship type and returned up to thousands of unrelated stars per query, degrading Full Hybrid precision below Spatial-Only in the ablation study. The fix constrains traversal to explicit 1-hop cluster membership: \texttt{Star}${\to}$\texttt{MEMBER\allowbreak\_OF}${\to}$\texttt{Cluster}${\leftarrow}$\texttt{MEMBER\allowbreak\_OF}${\leftarrow}$\texttt{Star}.

The \texttt{MENTIONED\_IN} edge count is now \textbf{2{,}820}, populated via the cluster-mediated heuristic (confidence=0.6) linking papers covering a cluster to the top-20 brightest member stars. This is a meaningful step forward, though the heuristic approach does not reliably attach paper nodes to specific stars beyond cluster membership. Replacing the heuristic linker with a trained astronomy NER pipeline remains the primary prerequisite for making the Full Hybrid configuration genuinely better than Hybrid (no graph).

\subsection{Uncertainty Propagation}
\label{sec:uncertainty}
%% ----------------------------------------------------------------

The repository includes utilities for attaching uncertainty estimates to derived physical quantities. For a star with Gaia $G$-band apparent magnitude $G$ and parallax $\parallax$ in milliarcseconds, the absolute magnitude is estimated via the distance modulus:
\begin{equation}
M_G = G - 5\log_{10}\!\left(\frac{d}{\SI{10}{pc}}\right)
     = G + 5 + 5\log_{10}\!\left(\frac{\parallax}{\SI{1000}{mas}}\right).
\label{eq:mg}
\end{equation}

Let $\sigma_G$ denote the uncertainty in $G$ and $\sigma_\parallax$ the uncertainty in $\parallax$. Treating these as independent, the first-order error-propagation (delta method) gives:
\begin{align}
\operatorname{Var}(M_G)
 &\approx \left(\pdv{M_G}{G}\right)^{\!2}\!\sigma_G^{2}
   + \left(\pdv{M_G}{\parallax}\right)^{\!2}\!\sigma_{\parallax}^{2} \label{eq:delta_method} \\[4pt]
 &= \sigma_G^{2}
   + \left(\frac{5}{\parallax \ln 10}\right)^{\!2}\!\sigma_{\parallax}^{2},
\end{align}
since $\pdv*{M_G}{G}=1$ and $\pdv*{M_G}{\parallax}=5/(\parallax\ln 10)$. This yields the propagated uncertainty
\begin{equation}
\sigma_{M_G} = \sqrt{\sigma_G^{2}
      + \left(\frac{5}{\parallax\,\ln 10}\right)^{\!2}\sigma_{\parallax}^{2}} .
\label{eq:mgerr}
\end{equation}

This approximation is useful for moderate fractional parallax uncertainty ($\sigma_\parallax / \parallax \lesssim 0.2$). For high relative parallax error, a full Bayesian treatment such as that of \citet{BailerJones2021} is preferable. \citet{BailerJones2021} show that naive parallax inversion introduces a bias of order $\sigma_\parallax^2 / \parallax$, which is negligible for parallax SNR~$>5$ but becomes severe for wide binaries, distant giants, or sources with $\parallax / \sigma_\parallax < 3$. Equation~\eqref{eq:mgerr} should be understood as a pilot-grade indicator, not a rigorous distance posterior.

\subsection{Provenance and Reproducibility}
\label{sec:provenance}
%% ----------------------------------------------------------------

The implementation records practical execution metadata: session identifier, UTC timestamp, query type, query parameters, system version (via pyproject.toml SHA-256 hash truncated to 16 characters), LLM model identifier, embedding model name, and backend hosts. The \texttt{ResearchProvenanceLogger} class exports a \texttt{.zip} session bundle containing a machine-readable \texttt{manifest.json} and all generated result files, suitable for attachment to a publication or sharing with collaborators.

This is sufficient for lightweight reproducibility of repository experiments. It is not a full W3C PROV-compliant provenance framework \citep{Belhajjame2013}.

A containerised verification pass was executed on 2026-04-27. It completed 18 focused unit tests via \texttt{pytest tests/test\_eval\_metrics.py} plus live HTTP validation of all major API endpoints. The containerised full suite records 50 passed tests. These checks establish runtime stability at prototype scale, while the broader archived benchmark numbers remain historical evaluation artifacts rather than freshly re-run measurements.

\section{Dataset Construction}
\label{sec:dataset}
%% ================================================================

The current working catalog holds 34{,}820 stellar objects drawn from Gaia DR3 \citep{Vallenari2023}, spread across 42 seeded sky regions. This section explains why, and what the selection strategy was.

Gaia DR3 contains approximately 1.3 billion sources. Running \textsf{TaarYa}'s full pipeline---which combines cone-search retrieval, vector embedding, graph ingestion, semantic search, and a ranking pass---against the entire catalog is not feasible for a research prototype on available hardware. The computational overhead of maintaining 1.3 billion star nodes in Neo4j, managing the corresponding graph edges, and running approximate nearest-neighbour search across billions of embedded vectors is well beyond what a prototype evaluation realistically requires. The 34{,}820-star subset was not drawn to be a random sample; it was drawn to be a \emph{representative} one.

\subsection{Sampling Strategy}
\label{sec:sampling}

The 42 seeded regions were chosen to cover a range of astrophysically distinct environments:

\begin{itemize}
    \item \textbf{Nearby open clusters} (Hyades, Pleiades, Coma Berenices, Praesepe): well-studied populations with known membership, useful for testing cluster-aware retrieval and membership-edge construction.
    \item \textbf{OB associations and young clusters} (Orion~OB1, NGC~2516, Alpha~Persei, IC~2391): regions with a mix of hot massive stars, pre-main-sequence objects, and embedded populations, exercising the colour-extreme and RUWE signal~families.
    \item \textbf{Magellanic Cloud fields}: distance extremes with sparse parallax signal-to-noise, exercising the uncertainty propagation limits discussed in Section~\ref{sec:uncertainty}.
    \item \textbf{High-latitude calibration regions}: low stellar density, useful for testing the local density signal (S6) and verifying that sparse-field queries return meaningful results.
    \item \textbf{Galactic Center direction}: crowded, high-extinction fields that challenge both the photometric correction module and the RUWE-based quality filter.
\end{itemize}

Within each region, all stars returned by a cone search satisfying a minimum parallax signal-to-noise ratio of $\parallax / \sigma_\parallax \ge 5$ were ingested. No magnitude or colour cuts were applied at ingestion time. The resulting sample preserves diversity in $G$-band magnitude (6 to 21), parallax (0.1 to 120 mas), and BP--RP colour ($-0.3$ to 4.2). This range is sufficient to exercise all seven signal families in the discovery ranker.

The 40 injected anomalous stars (10 high-RUWE, 10 blue outliers, 10 red outliers, 10 high proper motion) were placed into five synthetic benchmark clusters specifically to ensure the discovery benchmark has usable ground truth. Without injection, the anomaly density in a 34{,}820-star sample calibrated for nearby clusters is low enough that the discovery pass rate is threshold-limited rather than pipeline-limited.

\subsection{Why 34,820 Is Sufficient for System Validation}
\label{sec:sufficient}

The core claim of this paper is not about the fraction of sky covered; it is about pipeline behaviour. The evaluation questions we can answer with this dataset are: Does hybrid retrieval outperform spatial-only retrieval? Does the semantic subsystem handle multi-topic literature queries reliably? Does the ranking heuristic correctly prioritise anomalous stars when they exist? All three questions are answerable with a heterogeneous sample of tens of thousands of stars. None of them require a billion.

What the dataset cannot support is full-sky population statistics, completeness estimates, or claims about absolute anomaly rates across Gaia DR3. Those are future-work items, not claims made here.

\section{Discovery Ranking}
\label{sec:ranking}
%% ================================================================

The discovery ranker is a transparent, additive-signal heuristic prioritiser. It is not trained as a supervised classifier, and its output score is a ranking signal, not a calibrated posterior probability of astrophysical interest. The transparency is deliberate: a user can inspect which terms caused a star to rise in the ranking and adjust the profile accordingly.

%% ----------------------------------------------------------------
\subsection{Signal Families}
\label{sec:signals}
%% ----------------------------------------------------------------

The implementation uses seven independent signal families.

\medskip\noindent\textbf{(S1) Catalog-origin bonus.} Non-Gaia rows receive a fixed bonus $b_{\mathrm{cat}}$ because cross-catalog presence is a weak proxy for prior scientific attention.

\medskip\noindent\textbf{(S2) Astrometric quality (RUWE).} The Renormalised Unit Weight Error is a normalised $\chi^2$ from the Gaia astrometric solution \citep{Fabricius2021}. Elevated RUWE ($\ge 1.4$) can flag unresolved multiplicity, object confusion, or stellar activity. The scoring uses three thresholds:

\[
s_{\mathrm{ruwe}} =
\begin{cases}
b_{\mathrm{ruwe}}^{\mathrm{high}},  & \mathrm{RUWE} \ge 2.0, \\[2pt]
b_{\mathrm{ruwe}}^{\mathrm{elev}},   & 1.4 \le \mathrm{RUWE} < 2.0, \\[2pt]
b_{\mathrm{ruwe}}^{\mathrm{tight}}, & \mathrm{RUWE} < 0.9, \\[2pt]
b_{\mathrm{ruwe}}^{\mathrm{miss}},  & \text{RUWE unavailable}.
\end{cases}
\]

\medskip\noindent\textbf{(S3) Photometric colour extremes.} Blue or red $G_{\mathrm{BP}} - G_{\mathrm{RP}}$ values outside the main-sequence ridge are scored:
\[
s_{\mathrm{color}} =
\begin{cases}
b_{\mathrm{color}}, & (G_{\mathrm{BP}}-G_{\mathrm{RP}}) \le -0.1 \;\lor\; (G_{\mathrm{BP}}-G_{\mathrm{RP}}) \ge 2.8, \\
b_{\mathrm{nocolor}}, & \text{colour unavailable}.
\end{cases}
\]

\medskip\noindent\textbf{(S4) Kinematic signal.} Total proper motion $\mu = \sqrt{\mu_{\alpha^*}^2 + \mu_\delta^2}$ is compared against two thresholds:
\[
s_{\mathrm{motion}} =
\begin{cases}
b_{\mathrm{motion}}^{\mathrm{high}}, & \mu \ge \SI{80}{mas\,yr^{-1}}, \\[2pt]
b_{\mathrm{motion}}^{\mathrm{mid}},  & \mu \ge \SI{40}{mas\,yr^{-1}}, \\[2pt]
0, & \text{otherwise}.
\end{cases}
\]
The $\SI{80}{mas\,yr^{-1}}$ threshold targets hyperrunaway and hypervelocity star candidates \citep{Brown2015}.

\medskip\noindent\textbf{(S5) Brightness-distance inconsistency.} Apparent magnitude $G$ compared against the parallax-implied distance identifies objects that are either implausibly bright for their inferred distance or implausibly faint:
\[
s_{\mathrm{bright}\!-\!\mathrm{dist}} =
\begin{cases}
b_{\mathrm{bright}}, & G \le 10 \;\land\; d \ge \SI{500}{pc}, \\[2pt]
b_{\mathrm{bright}}, & G \ge 16 \;\land\; d \le \SI{50}{pc}.
\end{cases}
\]

\medskip\noindent\textbf{(S6) Local stellar density.} A bounded bonus proportional to the number of neighbours $k_i$ within a fixed angular radius:
\[
s_{\mathrm{density},i} = \min\!\bigl(\alpha\,(k_i - 1)_+,\; \alpha_{\max}\bigr),
\quad (x)_+ \equiv \max(x, 0).
\]

\medskip\noindent\textbf{(S7) Cross-match overlap.} A bounded affine function of the number $n_i$ of distinct catalog overlaps:
\[
s_{\mathrm{xmatch},i} = \min\!\bigl(b_0 + n_i\,b_1,\; b_{\max}\bigr).
\]

\subsection{Score Aggregation}
\label{sec:score_agg}
%% ----------------------------------------------------------------

For candidate $i$, the aggregate score sums all applicable signal terms, capped at $S_{\max}=100$:

\begin{equation}
S_i = \min\!\Bigl(\sum_{j=1}^{7} s_{j,i},\; S_{\max}\Bigr).
\label{eq:score}
\end{equation}

%% ----------------------------------------------------------------
\subsection{Robustness to Scoring Assumptions}
\label{sec:robustness}
%% ----------------------------------------------------------------

To characterise ranking stability under small weight perturbations, the repository includes a multi-seed Monte Carlo utility. For candidate $i$ over $M$ perturbation runs with weight perturbations drawn from a uniform distribution over $\pm\epsilon$ of each nominal weight:

\begin{equation}
\bar{S}_i = \frac{1}{M}\sum_{m=1}^{M} S_i^{(m)},
\qquad
\sigma_i = \sqrt{\frac{1}{M}\sum_{m=1}^{M}\bigl(S_i^{(m)} - \bar{S}_i\bigr)^2}.
\label{eq:robustness}
\end{equation}

Candidates with high $\sigma_i$ relative to $\bar{S}_i$ depend more heavily on exact weight assumptions and should be treated with greater caution. The current repository includes this as a diagnostic utility; the primary evaluation does not yet archive full robustness sweeps alongside benchmark results.

\begin{prop}[Monotonicity of the aggregate score]
For any two candidates $i$ and $j$, if every applicable signal weight for $i$ is at least as large as the corresponding weight for $j$ and at least one is strictly larger, then $S_i > S_j$ provided neither score is capped at $S_{\max}$.
\end{prop}
\begin{cor}
Adding a new signal family to a candidate strictly increases its score; removing one strictly decreases it. This ensures ranking consistency under profile substitution.
\end{cor}

%% ----------------------------------------------------------------
\subsection{Proper Motion Reference Frames}
\label{sec:pm}
%% ----------------------------------------------------------------

Gaia DR3 reports proper motions in the ICRS reference system. The total proper motion used in signal (S4) is the invariant scalar:

\begin{equation}
\mu = \sqrt{\mu_{\alpha^*}^2 + \mu_\delta^2},
\label{eq:pm}
\end{equation}

where $\mu_{\alpha^*} = \mu_\alpha \cos\delta$ corrects for meridian convergence. This is the standard invariant proper motion in spherical astronomy, appearing in kinematic diagnostics such as the Toomre diagram and the UV-plane distribution.

The $\SI{80}{mas\,yr^{-1}}$ threshold in the \texttt{strict} profile matches approximately the boundary used by \citet{Brown2015} to identify hypervelocity star candidates in GALAH DR3. Reaching $\mu > \SI{80}{mas\,yr^{-1}}$ at the distances of most Gaia stars requires either genuinely high tangential velocity ($\gtrsim \SI{600}{km\,s^{-1}}$ at 1 kpc) or proximity to the ecliptic poles. The \texttt{strict} profile is therefore most sensitive to genuine kinematic outliers in low-density fields near the ecliptic poles.

\subsection{Cluster Membership Graph Validation and Dilution Analysis}
\label{sec:membership_eval}
%% ----------------------------------------------------------------

A central architectural claim of graph-augmented astronomical retrieval is that entity relationships (such as \texttt{(Star)-[:MEMBER\_OF]->(Cluster)}) enrich candidate retrieval with astrophysical context. However, evaluating graph utility requires verifying that stored relationships reflect genuine astrophysical membership rather than spatial query artifacts.

We conducted a diagnostic audit comparing the database \texttt{MEMBER\_OF} edges against the seeding cone geometry across all benchmark clusters. The Jaccard similarity between the graph edges and the spatial cone query results,
\begin{equation}
J(E_{\mathrm{graph}}, C_{\mathrm{cone}}) = \frac{|E_{\mathrm{graph}} \cap C_{\mathrm{cone}}|}{|E_{\mathrm{graph}} \cup C_{\mathrm{cone}}|},
\end{equation}
was identically $1.000$ across all five seeded benchmark clusters (Hyades, Pleiades, Praesepe, Alpha Persei, NGC~2516). This diagnostic proves that the graph edges literally encoded ``was retrieved in the initial cone search'', rather than genuine astrophysical membership.

To quantify the resulting contamination, we cross-matched real Gaia DR3 cone queries ($G \le 18$, $\varpi / \sigma_\varpi \ge 5$) against the published open cluster census of \citet{Hunt2023} (selection probability $p \ge 0.7$). In full, uncurated Gaia DR3 cones, confirmed physical cluster members account for only $2.5\%$--$5.6\%$ of stars in the field ($2.58\%$ in Melotte~22 / Pleiades, $3.51\%$ in NGC~2632 / Praesepe, and $5.62\%$ in NGC~2516). Consequently, between $94.4\%$ and $97.4\%$ of stars in the cone-seeded graph were unrelated field stars.

This empirical finding directly explains the performance of the Full Hybrid configuration in Section~\ref{sec:ablation}: unranked 1-hop traversal across cone-seeded \texttt{MEMBER\_OF} edges dilutes precision because $95\%$--$98\%$ of the traversed stars are field interlopers rather than co-moving cluster members.

\subsection{Cluster Member Retrieval Benchmark on Real Gaia DR3 Cones}
\label{sec:retrieval_benchmark}
%% ----------------------------------------------------------------

To establish whether graph structures provide a genuine advantage for member recovery once field contamination is present, we formalized the cluster member retrieval task: given $N_{\mathrm{seed}} = 10$ confirmed cluster members drawn from gold catalogs \citep{Hunt2023}, rank the remaining stars in a real Gaia DR3 cone field to recover hidden members.

\paragraph{Leak-Free Protocol.}
Seeds are strictly removed from the candidate pool so that ranking seeds first receives zero credit. Every method receives the identical 3D astrometric input ($\mu_{\alpha*}, \mu_\delta, \varpi$), and evaluation is averaged over 5 independent random seed draws across real Gaia DR3 cone extractions (37{,}552 stars total; 1{,}336 gold members). We compare six retrieval strategies:
\begin{enumerate}
    \item \textbf{Cone Traversal (Base Rate):} Unranked retrieval of cone stars, corresponding to the original unranked graph edge traversal.
    \item \textbf{Seed Box (TOPCAT Baseline):} The classical astronomical baseline, defining a bounding window of $\pm k$ robust MAD standard deviations around the seed median in proper motion and parallax.
    \item \textbf{Seed Mahalanobis:} Ranking by Mahalanobis distance to the seed centroid using Ledoit--Wolf shrinkage covariance estimation \citep{Ledoit2004}.
    \item \textbf{Seed $k$-NN:} Distance to the $k$-th nearest seed ($k=3$).
    \item \textbf{Graph Personalized PageRank (PPR):} PageRank with restart probability $\alpha = 0.85$ rooted on the seed nodes over a $k$-NN similarity graph constructed in astrometric feature space.
    \item \textbf{HDBSCAN with Seeds:} Density-based clustering, ranking stars belonging to the cluster containing the majority of seeds.
\end{enumerate}

Crucially, Graph Personalized PageRank achieves $\text{AP} = 0.868$, which is statistically indistinguishable from the simple TOPCAT Seed Box baseline ($\Delta\text{AP} = -0.007$, 95\% CI [$-0.029, +0.011$], spanning zero). This provides a clear, honest architectural conclusion: graph propagation does not outperform classical statistical and metric-distance methods for astrometric cluster member retrieval. The utility of graph databases in astronomy systems lies in multi-catalog entity resolution, literature-to-source provenance, and relational linking, rather than replacing Euclidean distance metrics on low-dimensional astrometric spaces.

\subsection{Exoplanet Candidate (TOI) Vetting and Field Crowding}
\label{sec:toi_vetting}
%% ----------------------------------------------------------------

A common hypothesis in automated transit vetting is that spatial neighbor catalog queries (e.g., checking for nearby bright companions in Gaia DR3) can reliably identify false positives caused by background eclipsing binaries (NEBs). We tested whether incorporating a Gaia DR3 neighbor-density metric ($\text{ratio} = \sum 10^{-0.4(G_i - G_{\mathrm{target}})}$ within $21''$) provides meaningful predictive power for transit vetting beyond target-star parameters.

\paragraph{Dataset and Protocol.}
We evaluated 8{,}151 TESS Objects of Interest (TOIs) from the NASA Exoplanet Archive, containing 1{,}421 confirmed exoplanets and 1{,}315 confirmed astrophysical false positives. Models were evaluated using 5-fold Stratified Group $K$-Fold cross-validation (grouped by TIC ID to avoid multi-planet transit leakage), repeated over 5 random splits.

To prevent baseline handicapping, we constructed a multi-covariate baseline using target properties: transit depth ($\delta_{\mathrm{ppm}}$), TESS magnitude ($T_{\mathrm{mag}}$), orbital period ($P$), transit duration ($T_{\mathrm{dur}}$), and absolute Galactic latitude ($|b|$). Galactic latitude serves as an essential astronomical proxy for stellar crowding.

\begin{enumerate}
    \item Incorporating Galactic latitude ($|b|$) increases baseline AUC from $0.653$ to $0.740$, proving that line-of-sight crowding is a primary astronomical confounder in transit false-positive rates.

\end{enumerate}

These empirical findings demonstrate that spatial neighbor checks from general catalog queries do not provide substantial marginal vetting power beyond target brightness and Galactic crowding. In the resubmitted manuscript, we report this null result transparently: specialized transit-vetting pipelines (e.g., pixel-level PRF centroid analysis) remain essential for definitive false-positive elimination.

\subsection{Methodological Integrity: Synthetic Calibration vs.\ External Truth}
\label{sec:synthetic}
%% ----------------------------------------------------------------

The benchmark suite in Section~\ref{sec:results} contains 560 synthetically injected stars and verifies that discovery-ranked candidates satisfy user-specified physical thresholds (for example, $\mu > \SI{80}{mas\,yr^{-1}}$). We emphasize that this is a useful internal consistency check and diagnostic calibration, but it is not external scientific validation. A candidate that passes the threshold has \emph{measured} high proper motion; it has not been independently confirmed as a hypervelocity or hyperrunaway star. That requires radial-velocity measurements, kinematic traceback, and comparison against Galactic potential models \citep{Brown2015, ElBadry2021}. 

By contrast, the cluster member retrieval evaluation (\S\ref{sec:retrieval_benchmark}) and exoplanet vetting evaluation (\S\ref{sec:toi_vetting}) utilize external, peer-reviewed ground-truth catalogs (Hunt \& Reffert 2023 open cluster memberships; NASA Exoplanet Archive confirmed TOIs). The paper strictly demarcates between internal synthetic calibration and externally validated scientific discovery.

The inlist includes initial mass (estimated from BP--RP colour and $M_G$ via main-sequence mass-luminosity relations), metallicity $Z$ (from catalog provenance: SMC/LMC/field), effective temperature (from colour-temperature relations), and surface gravity $\log g$ (from mass via main-sequence approximation). The generated inlist is a \emph{validated starting point} for MESA evolution runs; it does not claim precision equivalent to spectroscopic parameter determination.

\section{Scalability and Deployment Considerations}
\label{sec:scalability}
%% ================================================================

The current working corpus of 34{,}820 stars is a deliberate evaluation subset, not an architectural ceiling. The pipeline components were chosen for their ability to scale to much larger catalogs, and this section explains what that path looks like in practice.

\subsection{Vector Retrieval Scaling}

Qdrant's HNSW indexing \citep{Malkov2020} is the backbone of the semantic backend. HNSW graph construction scales approximately as $O(N \log N)$ in index build time and $O(\log N)$ in query time, and Qdrant supports horizontal sharding across multiple nodes via its distributed mode. The 6{,}464 embeddings currently indexed are a tiny fraction of what the system can accommodate; Qdrant deployments routinely handle hundreds of millions of vectors with sub-second query latency at commodity hardware costs. Scaling the literature corpus to cover all ArXiv astronomy papers (currently around 300,000 papers on astro-ph) would require a one-time re-ingestion pass and a larger Qdrant instance. The ingestion pipeline is already designed for batch resumable operation.

\subsection{Catalog Ingestion Scaling}

The PostgreSQL/Q3C spatial backend can handle full Gaia DR3 in principle. Q3C was designed for this scale---the Sloan Digital Sky Survey used PostgreSQL/Q3C for catalog access at comparable row counts \citep{York2000}. The practical bottleneck for moving from 34{,}820 to $10^9$ rows is bulk ingestion time and disk I/O, not query performance. Q3C cone-search query time scales as $O(\log N)$, so retrieval latency changes modestly even at billion-row scale.

\subsection{Graph Database Scaling}

Neo4j's native graph storage scales to tens of billions of nodes and relationships in enterprise configurations. The current graph with 34{,}820 star nodes and 28{,}881 \texttt{MEMBER\_OF} edges is well within single-instance capacity. Expanding to full Gaia DR3 would require partitioning the graph by sky region or cluster, which is architecturally straightforward given that the current cluster-membership edge structure already provides natural partition boundaries.

\subsection{Scalability Projection}

These projections assume single-node deployment; distributed configurations would reduce these figures.

\subsection{Batch Processing and Future Deployment}

Full Gaia DR3 ingestion could proceed in batches by sky region, using the existing \texttt{POST /api/ingest/graph} endpoint and the resumable Qdrant batch upsert pipeline. A parallel ingestion run with, say, 100 workers each responsible for one sky tile is architecturally compatible with the current design and would bring total ingestion time to the order of hours rather than weeks. This is future work, but it is future work on a clear path---not a redesign.

\section{Discussion and Limitations}
\label{sec:discussion}
%% ================================================================

The novelty of \textsf{TaarYa} is in its software architecture: a hybrid retrieval layer with transparent ranking and astronomy-compatible export. The ablation study (Table~\ref{tab:ablation}) provides quantitative evidence that hybrid (spatial+semantic) retrieval outperforms single-backend baselines by $+46.2\%$ in P@10 and $+33.3\%$ in MRR.

The benchmark harness is informative but limited. Unsupported prompt types, schema mismatches, and partial constraint handling currently limit the evidential strength of several reported numbers. The IR-metrics ablation study provides a more robust evaluation.

The 2026-04-29 hardening pass fixed a critical graph-traversal regression where \texttt{find\allowbreak\_related\allowbreak\_stars()} used a wildcard \texttt{[*1..2]} path that matched any relationship type and returned thousands of unrelated stars, degrading Full Hybrid precision below Spatial-Only. The fix constrains traversal to explicit 1-hop cluster membership:
\[
\texttt{Star}\xrightarrow{\texttt{MEMBER\_OF}}\texttt{Cluster}\xleftarrow{\texttt{MEMBER\_OF}}\texttt{Star}.
\]
Even after this correction, Full Hybrid returns co-cluster members that are not preferentially anomalous, diluting P@10 under anomaly-based ground truth. A more comprehensive entity-linking strategy---fine-tuned astronomy NER models or a dedicated entity-resolution service \citep{Shen2015}---is needed before the graph layer becomes a mature discovery component.

Sky coverage is partial. The verified runtime exposes 13 seeded sky regions through the public API and 29{,}798 catalog rows in PostgreSQL/Q3C. This footprint spans nearby clusters, Magellanic Cloud fields, and calibration regions, but it is a subset rather than a full-sky survey.

External scientific validation is absent. The repository contains internal utilities for score perturbation and synthetic threshold checks, but these are not substitutes for validation against independent expert-curated catalogs such as binary-star samples \citep{ElBadry2021} or hypervelocity-star samples \citep{Brown2015}. That validation is future work.

Time-domain integration is implemented but unevaluated. The repository includes an alert ingestion pipeline for the Transient Name Server (TNS) and ALeRCE broker \citep{Forster2021}, creating \texttt{Alert} nodes in the graph with spatial cross-matching to Gaia stars. This should be treated as a prototype capability.

\section{Conclusions}
\label{sec:conclusions}
%% ================================================================

\textsf{TaarYa} is a hybrid retrieval and workflow-support layer for astronomy research. Its validated contributions are:

\begin{enumerate}
    \item A hybrid architecture combining spatial (PostgreSQL/Q3C), semantic (Qdrant), and graph (Neo4j) retrieval behind a unified orchestration layer, with ablation evidence showing $+46.2\%$ P@10 and $+33.3\%$ MRR improvement over spatial-only baselines using leak-free ground truth.
    \item A transparent discovery-ranking heuristic with three configurable profiles and complete published weight tables, together with a formal first-order uncertainty propagation for derived absolute~magnitudes.
    \item Astronomy-compatible export and handoff through REST (GET and POST), VOTable, CSV, JSON, and SAMP, together with helper modules for DS9 region files, MESA stellar-evolution inlists, CASA measurement-set cross-matching, and time-domain alert integration.
    \item A graph auto-sync layer maintaining Neo4j consistency with the primary PostgreSQL/Q3C and Qdrant backends across all ingestion~paths.
    \item A repository-level evaluation artifact comprising a 50-query benchmark (100\% semantic pass rate), formal IR-metric ablation tables with leak-free ground truth, 50~automated regression tests, and live HTTP verification~scripts.
    \item A representative evaluation corpus of 34{,}820 stars from Gaia DR3 spanning 42 sky regions and covering diverse magnitude, parallax, and colour distributions, with a clear architectural path to full-catalog scaling.
\end{enumerate}

The ablation study shows that hybrid retrieval produces substantially better results than any single backend. The honest central conclusion is that external scientific validation and graph entity linking remain incomplete---specifically, the \texttt{MENTIONED\_IN} edge population is heuristic-based and represents the primary open bottleneck. But the quantitative retrieval improvement, the 100\% semantic pass rate, the breadth of implemented workflow integrations, and the verified live workflow surface across 13 seeded sky regions make \textsf{TaarYa} defensible as a research-software contribution with a concrete path toward stronger claims in its next iteration.

\section{Simplified Discovery-Ranking Pseudocode}
\label{app:scoring}

Listing~\ref{lst:score} presents the core scoring logic. Full deduplication, database export, and API surface details are omitted for brevity.

\begin{lstlisting}[language=Python, caption={Simplified discovery-ranking pseudocode. Profile weights are defined in Table~\ref{tab:profiles}.}, label={lst:score}]
def score_candidate(star: dict, profile: dict) -> tuple[float, list[str]]:
    score = 0.0
    reasons = []

    # S1: catalog bonus
    if star["catalog_source"] != "GAIA":
        score += profile["catalog_bonus"]
        reasons.append("non-Gaia catalog object")

    # S2: RUWE
    ruwe = star.get("ruwe")
    if ruwe is None:
        score += profile["ruwe_missing"]
    elif ruwe >= 2.0:
        score += profile["ruwe_high"]
        reasons.append("high RUWE")
    elif ruwe >= 1.4:
        score += profile["ruwe_elevated"]
        reasons.append("elevated RUWE")
    elif ruwe < 0.9:
        score += profile["ruwe_tight"]
        reasons.append("tight RUWE")

    # S3: colour extremes
    bp_rp = star.get("bp_rp")
    if bp_rp is not None and (bp_rp <= -0.1 or bp_rp >= 2.8):
        score += profile["color_extreme"]
        reasons.append("extreme colour")

    # S4: proper motion
    pm = sqrt(star["pmra"]**2 + star["pmdec"]**2)
    if pm >= 80.0:
        score += profile["motion_high"]
        reasons.append("fast proper motion")
    elif pm >= 40.0:
        score += profile["motion_mid"]
        reasons.append("notable proper motion")

    # S5: brightness-distance anomaly
    g, dist = star["phot_g_mean_mag"], star["distance_pc"]
    if (g <= 10 and dist >= 500) or (g >= 16 and dist <= 50):
        score += profile["brightness_anomaly"]
        reasons.append("brightness-distance inconsistency")

    # S6: local density
    k = star.get("neighbour_count", 0)
    density = min(profile["density_scale"] * max(k - 1, 0),
                  profile["density_cap"])
    score += density

    # S7: cross-match
    n = star.get("catalog_overlaps", 0)
    xmatch = min(profile["cross_match_base"] + n * profile["cross_match_per_catalog"],
                 profile["cross_match_cap"])
    score += xmatch

    return round(min(score, 100.0), 1), reasons
\end{lstlisting}
